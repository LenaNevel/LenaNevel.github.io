RowliPurli — Knitting Project Manager (PWA)

Live at rowlipurli.com

Live in Production 0→1 Product Next.js 16 / React 19 Offline PWA

Context

Knitters track row counts, yarn, and gauge across paper notes, spreadsheets, and phone timers, and the apps that exist feel like cluttered dashboards rather than a calm companion. I designed, built, and publicly released RowliPurli solo — product, design, and engineering — while working full-time. It is live at rowlipurli.com and still actively developed.

Product & Design Decisions

  • Positioned as "The Knitting Bag for your Phone" — installable to the home screen and usable offline, because knitters work away from a desk and often without signal
  • Built a warm design system (burnt rust / terracotta / cream, Lora + Inter) with light and dark mode, tuned so accent fills always carry a contrast-safe foreground
  • Calm-first UX: one-tap counters for rows, repeats, and shaping rounds; generous whitespace; microcopy that guides rather than blames
  • Every destructive action routes through a shared confirm dialog that spells out cascading impact before anything is removed

Architecture & Engineering Judgment

  • Stack: Next.js 16 App Router + React 19, TypeScript with no any, Tailwind CSS 4 tokens, Supabase (PostgreSQL + magic-link auth) with row-level security, TanStack Query
  • Reverted my own optimization: a cache-first service worker shipped cross-device stale-data bugs — a service-worker cache on someone's phone is unreachable from the server, so a write on one device cannot invalidate another's copy, and one route held many independently-expiring cache entries. Reads are now network-first with cache strictly as an offline fallback
  • Storage integrity: shared chart images are deleted only once no row still references them, since Postgres cascades never reach object storage and the keys are unrecoverable afterward
  • Schema discipline: 14 versioned, idempotent migrations against a frozen bootstrap snapshot, with separate dev and production projects
  • Payments: Stripe Embedded Checkout for optional donations, intentionally with no webhook or donor persistence — success is confirmed by re-retrieving the session server-side

Scale & Outcomes

  • Publicly released and running in production on Vercel with a custom domain and branded transactional email
  • ~19,000 lines of TypeScript across 229 modules and 22 routes
  • 235 commits in roughly four months, shipped alongside a full-time senior engineering role
  • Feature-based architecture (projects, parts, steps, counters, gauge book, yarns, donations) built for continued iteration

Storage Integrity Guard

TypeScript Supabase Failure Modes

From RowliPurli. Copying a part carries a chart image's key to the copy instead of duplicating the file, so one stored object can be referenced by several rows — and a naive delete would blank a chart another part still shows. Every removal first asks whether it is the last reference. When the lookup itself fails, it deliberately errs toward keeping the file: a leaked object costs storage, a wrong removal costs a knitter their chart.

// Copying a part carries a Diagram step's image_path to the copy rather than
// duplicating the file, so one Storage object can be referenced by several step
// rows. Removing it whenever any single step lets go would blank the picture the
// other steps still show, so every removal asks first whether it is the last one
// holding the key.

const KEYS_PER_LOOKUP = 100;

// The subset of `keys` that some step row still points at. Errs toward
// "referenced": a failed lookup can't tell a live key from a dead one, so its
// whole chunk is kept. A leaked object costs storage; a wrong removal costs a
// knitter their chart.
async function stillReferenced(
  supabase: SupabaseClient<Database>,
  keys: string[],
): Promise<Set<string>> {
  const referenced = new Set<string>();

  for (let i = 0; i < keys.length; i += KEYS_PER_LOOKUP) {
    const chunk = keys.slice(i, i + KEYS_PER_LOOKUP);

    const [partSteps, swatchSteps] = await Promise.all([
      supabase.from("part_steps").select("image_path").in("image_path", chunk),
      supabase.from("gauge_swatch_steps").select("image_path").in("image_path", chunk),
    ]);

    if (partSteps.error || swatchSteps.error) {
      for (const key of chunk) referenced.add(key);
      continue;
    }

    for (const row of [...(partSteps.data ?? []), ...(swatchSteps.data ?? [])]) {
      if (row.image_path) referenced.add(row.image_path);
    }
  }

  return referenced;
}

export async function removeStepImagesIfUnreferenced(
  supabase: SupabaseClient<Database>,
  paths: readonly (string | null | undefined)[],
): Promise<void> {
  const keys = [...new Set(paths.filter((path): path is string => !!path))];
  if (keys.length === 0) return;

  // Never throws. Callers reach here with their row work already committed, so a
  // lookup or removal that fails leaves an orphaned file — the accepted trade
  // — rather than reporting a failure for a delete that actually succeeded.
  try {
    const referenced = await stillReferenced(supabase, keys);
    const removable = keys.filter((key) => !referenced.has(key));
    if (removable.length === 0) return;

    await supabase.storage.from(STEP_IMAGES_BUCKET).remove(removable);
  } catch {
    // Orphan left behind; what the knitter asked for still happened.
  }
}
